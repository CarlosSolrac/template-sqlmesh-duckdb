### ADR-0007: Build each run on a copy of the warehouse and swap it in only when the run succeeds
- Status: Accepted
- Date: 2026-10-22
- Context: Restating a `FULL` model rebuilds its prod table in place, so when an audit fails the table already holds the rows the audit rejected. For the staging model this was an accepted exception; for the mart (design.md finding 2) it meant consumers could read rows a blocking audit rejected while the log said otherwise. The warehouse file also holds SQLMesh's state, so a copy of the file is a consistent copy of data and state.
- Decision: `StagedWarehouse` copies `data/warehouse.duckdb` to `data/.build/data/warehouse.duckdb` before a run. The whole run (ingestion and both plans) works on the copy, with `data/.build` as the working directory, which is where SQLMesh resolves `config.yaml`'s relative database. When every plan applied, the copy replaces the live file with one `os.replace`; otherwise the live file is not touched and the copy is kept as `data/warehouse.failed.duckdb`, replacing an earlier one, so the rejected rows can be queried.
- Alternatives: restore a backup of the live file after a failure, rejected because the live file is modified during the run and a crash would leave it half built; run the plans in a SQLMesh dev environment first, rejected because SQLMesh cannot restate models whose current version is used in production outside prod; stage the mart in a second table that a final model swaps in, rejected because every mart would need the same pattern.
- Consequences: The live warehouse never holds rows an audit rejected, and a crashed run leaves it intact. Each run copies the whole file, which costs time and disk in proportion to its size; revisit with the volumes of design.md open question 1. Rows that failed an audit are no longer queryable in the live warehouse, only in `warehouse.failed.duckdb`. `data/.build` and the failed copy are git-ignored with `data/`.
